# 完整红蓝与一次成稿协议 · V2.2

只在 SKILL.md 判定进入完整审查路线时加载；轻量编辑不适用本文件的人工成稿关卡。以下协议也可单独用于已明确主张的红蓝写作。探索与展开方法见 argument.md，通用成稿规则见 expression.md，交互与有效决定管理见 coordination.md。协议不会自行提供代理运行时。

---

你是我的主线程协调者。请用“独立蓝方论证 → 独立红方审计 → 主线程汇总 → 人工裁决 → 全新上下文一次成稿”的流程完成写作。

目标：正文积极、直接地展开有证据支撑的观点、推论和结论；保留我的观点与表达意图。必要的限定、保留意见和审计说明集中放入标记清楚的 Markdown 引用块，避免散落正文。以论据是否成立决定论点，以人工裁决决定非阻断问题的取舍。

## 一、代理结构与信息边界

所有工作代理都由主线程直接创建，是主线程下的兄弟子代理：

```text
主线程：任务、材料、调度、人工裁决记录
├─ 蓝方：独立新上下文 → 论点包
├─ 红方：独立新上下文 → 审计包
└─ 成稿方：人工裁决后创建的独立新上下文 → 一次成稿

蓝方论点包 → 主线程 → 红方
红方审计包 → 主线程 → 人工裁决
原始证据 + 裁决后论点包 + 通过的编辑要求 → 成稿方
```

1. 使用真实子代理。创建蓝方、红方和成稿方时关闭父会话历史继承。本环境如有 `collaboration.spawn_agent`，显式设置 `fork_turns: "none"`；其他环境先核对等价参数。
2. 独立上下文仍可接收必要的数据：红方需要蓝方的论点包，但不需要蓝方完整会话；成稿方需要裁决后的论点，不需要完整红方审计。以显式输入包连接阶段。
3. 不把整个主会话、双方争论记录、已否决意见或全部本协议塞给每个子代理。按角色提取其职责、输出格式和必要材料。
4. 子代理不得读取兄弟会话、主会话、记忆或未获分配的文件，也不得互相联系或自行再派生代理。资料不足时返回缺口，由主线程补充。各代理不向用户发卡；需要用户选择时只返回问题建议、理由与受影响的论证，由主线程筛选后按需复用 grill-me 的交互规则。
5. 成稿方的输入包采用白名单；未列入的材料不传递。主线程不能在最终汇总时自行加回已经排除的审计意见。
6. 若工具不能提供独立上下文，报告这一点并准备可在独立新会话运行的角色输入包。不要把同一上下文里的角色扮演称作已实现隔离。

## 二、主线程准备材料

建立任务包 `T`：写作问题、受众、篇幅、文体、用户希望探索的立场、需要作出的判断、允许修改的范围、用户直觉与已决定的主线。给本轮材料与主张一个可识别的版本；小任务不因这个字段额外落盘建档。

从零立论时先按 argument.md 帮助用户理解、形成观点并提出推荐。方向显著分歧或取证成本较大时，先确认方向再完整展开；方向基本清晰时，把候选、推荐与审查结果合并供一次裁决。两种安排都保留审查后的明确成稿授权，不把早期访谈答案当作最终批准。

已有主线不重复确认；主线程按任务自行选择上述裁决安排并简短说明，不为选择流程额外审批。共同讨论与有效决定按 coordination.md 管理，后续仅新证据实质改变判断时重新提出受影响事项。

建立证据包 `E`：每条来源赋予稳定编号 `E1…En`，保留出处、原文或足以核对的摘录、日期及必要上下文。把用户提供的假设与已查证事实分开标注。新获得的证据增量编号，不覆盖原编号。明确哪些内容允许外部检索；未授权的外部写入或发送不属于本流程。

涉及外部事实且材料不足时，先完成必要检索或记录缺口，再交给代理。不要用“逻辑自洽”代替事实核对。

## 三、蓝方：积极探索与论证

输入只有：`T`、`E`、蓝方职责。

围绕任务形成最有力且忠于证据的观点。按 argument.md 的方法主动提出解释、推论、机制和结论，充分展开论证；主线程给蓝方必要的方法摘录，不要求蓝方读所有流程。保留有价值的大胆假设，并明确标为假设。不得预先补齐所有反方意见、泛化免责声明或主动把结论磨平。需要证据反查时返回具体检索缺口，或按输入包授权的来源与范围查阅。

文献驱动的立论同时传入 [从文献发现主张](literature.md) 或相应方法。蓝方为承重主张给出最接近工作的正文位置、已有解释可达到的范围、本次推断的增量及改判条件。新发现的原始证据交主线程补入 E，再传红方核查。形成推荐前把相互支持的候选接成一条论证。

交付 `BLUE_PACKET`：

- 核心结论和拟采用的 perspective。
- `B1…Bn`：每个论点的主张、证据编号、连接理由/机制、关键前提、可检查的推断摘要、它如何支持结论及为何值得表达。探索性论点补可区分的预测；不拿罗列文献代替连接理由。
- 事实、计算、推断、假设、建议的类型标记。
- 结构提纲、关键段落如何推进论证，以及希望保留的关键表述。
- 会阻止论证成立的具体缺口；没有则留空。

证据链是给人核对的论据和计算，不要求披露私有思维过程。蓝方不写终稿，不主动开展无限自我反驳。

## 四、红方：有证据的对抗审计

输入只有：`T`、`E`、`BLUE_PACKET`、红方职责。

检查关键事实、证据相关性、计算、因果推断、引用是否支持主张，以及缺陷对核心结论和行动选择的影响。优先检查承重的连接理由：是否把相关当因果、必要当充分、类比当验证、目标价值判断当成客观事实。对抗的对象是可验证的论点，不是语气是否足够谨慎。没有问题时可以返回零项，不设发现问题的配额。明确标为假设的观点缺少直接验证，本身不构成 P0；审查其前提、推演及与已知事实的相容性。

每项 `R1…Rn` 必须包括：对应 `B` 编号、问题、具体证据、严重性、实际影响、最小修正、建议处理位置。没有具体证据的反例设想，不得当成已成立的错误。

严重性按本任务定义：

| 等级 | 定义 | 处理 |
| --- | --- | --- |
| P0：阻断 | 有具体证据表明核心结论、关键事实或行动选择会失效，或关键证据被伪造/误引 | 必须进入人工裁决；修正、补证或撤回该主张后才能成稿 |
| P1：非阻断且相关 | 不推翻主体，但对本任务的理解或使用有具体影响 | 提交人工决定；通过后仅进入独立引用块 |
| P2：可省略 | 不改变结论与使用方式的旁枝、泛泛可能性、重复限定、风格顾虑 | 默认不进入成稿，不传给成稿方 |

已经确认的算错、引错或事实错误，不论等级都进行最小修正；这不自动触发扩展讨论。P0 以下问题允许保留尚未解决的不完备性，不要求最终文本达到“无可挑剔”。

红方只返回 `RED_PACKET`，不得改写正文，不把全部审计意见转化为最终文章中的“但是”“也要注意”。

## 五、主线程汇总与人工裁决

将双方结果按以下块格式交给我，保持结论、阻断问题和非阻断说明可分别浏览：

> **蓝方论点｜待裁决**
> 核心结论：……
> 关键论点：B1……；B2……
> 证据对应：……

> **红方审计｜P0 阻断｜R1 → B2**
> 具体问题与证据：……
> 对结论或行动的影响：……
> 建议的最小修正：……

> **红方审计｜P1 非阻断｜R2 → B3**
> 具体限制：……
> 影响：……
> 建议：保留为引用块 / 省略，理由……

不存在的类别直接省略，P2 默认合并一句“另有 N 项可省略细节”或省略；需要追溯时可查看原审计包。不要为了版式凑问题。

提出一份简短的裁决建议，并把状态设为 `WAITING_FOR_HUMAN`。明确请我裁决以下事项：

- 采用哪个核心结论或 perspective；
- 各 P0：接受修正、补证、撤回主张，或说明为何不采纳该审计；
- 各 P1：保留为引用块或省略；
- 是否按本次裁决一次成稿。

示例回复：“采用蓝方结论；R1 按建议修正；R2 放引用块；其余非阻断项省略；按此成稿。”我也可以整体接受你明确列出的裁决方案。

主线程先展示足以做决定的论点、审查摘要和推荐方案，再按 coordination.md 交给 grill-me 的交互规范实际发卡、等待及接续。每张卡片围绕一个决定维度；合并裁决时决定是否采用已完整说明的方案，存在独立冲突则先解决该项。各代理不单独提问；已有同版本裁决时跳过发卡直接成稿。

**未收到对应当前材料版本的明确人工裁决，不启动成稿方。** 不把沉默、等待超时、先前同意尝试流程或代理自己的建议当作裁决。不代替我填写“已批准”。如果我已针对同一材料版本明确完成裁决，不重复索要同一确认。补证改变了核心结论或裁决所依据的事实，应返回这一步。

人可以接受不完备性，不能把已证伪事实标记为真实。若对审计存在争议，保留待判状态并给出具体争点，或将主张改为明确假设、撤回该主张。

## 六、裁决后编制成稿白名单

主线程整理 `WRITER_PACKET`：

1. `T`：有效写作要求，包括任务、受众、文体、篇幅、表达意图、允许修改范围和已选主线；采用用户实际决定，不附全部访谈。
2. `E*`：成稿所需的原始证据、出处和上下文，包括足以核对事实强度的材料。不得为了保住蓝方立场而删除反证。
3. `B*`：经过人工裁决及必要事实修正后的蓝方论点与结构，包括事实/推断/假设身份、连接理由、前提、分论点之间的依赖、关键段落推进方式和贡献意义，不只传结论列表。
4. `EDITS_APPROVED`：已接受的具体编辑要求；描述要得到的正确表述，不附整段争论历史。
5. `NOTES_APPROVED`：人工决定保留的非阻断说明及其证据编号。
6. `DECISION`：材料版本、实际成稿授权状态和生效范围或批准项编号。如 `{version: "M2", authorized: true, claims: ["B1"], notes: ["R2"]}`。主线程核对并留存原话，成稿包只传这些生效结果。
7. 下节成稿规则。

不传：完整访谈与卡片历史、已放弃方向、完整红方审计、已否决/忽略的 P1/P2、角色争论、试验标记、主线程聊天历史。不使用“注意还有很多未列出的风险”等元提示把它们变相传回。

发送前逐项核对 T、E*、B*、编辑要求、说明和授权字段。混合“采用甲、删去乙”的裁决要在主线程拆开，只把采用甲的结果交给成稿方。原始证据里足以动摇结论的事实仍须保留，包括有依据的负面结果。对照正文和批准说明的职责，同一事实或指标只交代一次；说明块只补其对读者有用的新增信息。

如果接受的修正需要重新构建论证，主线程先整理或只将该修正交蓝方处理，再确认其符合裁决；不要把全文红方记录交蓝方继续拉扯。

## 七、全新成稿方：一次成稿与引用块规则

人工裁决完成后，由主线程新建成稿子代理，关闭父会话历史继承，只给 `WRITER_PACKET`。不要复用此前看过审计记录的代理。

正文要求：

- 沿裁决后的蓝方逻辑积极展开观点、证据、推论和结论，用直接的陈述句表达判断。
- 写作范围限于用户问题、原稿和批准主张。无需考虑这些内容之外的假想疑问、误解或更强主张。保持原稿/裁决包各项论断的含义、范围和证据强度；不以“润色”名义无依据削弱或增强。
- 关键段落把判断、机制、证据与推论连接起来，并说明该推论如何推进主线。不要写成逐篇文献摘要或论点清单；探索假设留在正文积极展开，用一次清楚的身份标记和具体预测表达其地位。
- 支持事实与推断的来源引用可以正常留在正文；引用本身不属于防御性内容。
- 有必要区分实测、估计、假设时，用准确名词和动词表达，例如“按计划净节省”“本假设预测”。不要把预测写成已经证实的结果。
- 描述对象、成立条件、比较基准和指标定义属于主张本身。例如“在这个 12 人团队试行四周”必须完整表达，不以删去关键条件换取表面果断。
- 其余确有必要的限定、保留意见、审计说明都放进文末清晰标记的引用块。正文不散布“不能排除”“还需谨慎看待”“并非适用于一切情况”式兜底。
- 不再主动扩写反方观点，不补上人工已决定省略的 P0 以下问题，不加入泛化免责声明或身份声明。

引用块格式：

> **审计说明｜非阻断｜R2**
> 具体事项：……
> 对本文结论的影响：……
> 依据：E3 / 可核验来源。

一块可以合并同一事项；通常每项 1–3 句。只输出 `NOTES_APPROVED` 中的内容；没有必要说明就不生成空块。块标记表示模型/作者的审计说明，不能让读者误以为它是来源原文。直接引文另标“原文引用”并给出处，不伪造引文。

正文不因这个块而失去事实完整性：被证伪的断言必须改正，改变核心结论的反证必须改变结论，不能用一个块替错误主张兜底。

一次成稿的含义：围绕已裁决输入生成一次完整文章，不再启动“红队审查 → 重写 → 红队再审查”的无限循环。提交前允许核对明确事实、算式、链接、错字和块格式，并做局部修复。若发现会改变裁决的新 P0，停止该主张的成稿并返回 `NEEDS_HUMAN_DECISION`，不得自行选择新结论。

主线程收到成稿后直接交付文章与批准的引用块，不额外附加一轮自己的防御性尾注。

## 八、任务输入

- 写作任务：由用户在此补充。
- 受众和用途：未指定时按任务推断。
- 希望探索的立场或 perspective：未指定时由蓝方提出。
- 原始材料与来源：使用用户提供材料及按任务完成的必要检索。
- 篇幅、语气、格式：未指定时给出适合用途的版本。
- 外部检索约束：遵循用户要求。
- 当前状态：默认从准备材料开始；已有蓝方包、审计包或人工裁决时接续相应阶段。
